# 缺陷修复

## 目标

用最短可靠路径定位并修复 bug，给出根因、改动和最小复测证据。

## 门禁

继续：

- 能确认问题现象，或能通过日志、代码路径、测试失败定位到可验证的缺陷方向。
- 能判断本次只是修复缺陷，不需要扩展成新需求。

暂停：

- 期望行为本身不明确，且代码 / 文档无法推断。
- 修复需要改变业务规则、数据口径、权限口径或对外契约。
- 正确修复明显超出当前授权范围。

## 工作重点

缺陷修复是单一能力，不主动编排自动化开发流程。把 bug 修好即可，不扩大需求，不顺手重构无关代码。

先确认：

- bug 表现。
- 期望行为。
- 相关代码路径。
- 影响面。

可以参考：

- 问题现象、报错信息、日志、截图、复现步骤。
- 期望与实际结果。
- 影响入口：页面、接口、任务、队列、配置、权限、缓存、数据。
- 最近改动、分支、提交、diff。
- 对应功能目录下的 `AI_DOC/features/`、`progress.json`、失败测试、测试报告和代码评审。

没有则跳过。信息不足时，先从代码、日志、测试、项目文档和历史实现查证；只有会影响业务口径或修复方向的关键事实无法判断时才暂停。

未知根因时，先做最小定位：复现、查日志、读相关代码、搜索历史实现、运行相关测试。不要在没有证据时直接猜修。

## 系统调试规则

行为类 bug 优先补 RED 证据：失败测试、复现命令、接口响应、日志、截图或最小复现步骤，至少证明旧路径确实失败。无法补 RED 证据时，必须说明原因，并记录替代证据，不能把推断当成已复现。

每次修复只验证一个主要假设。一次“修复尝试”指：基于某个假设改代码，并执行对应验证后仍失败。

连续 3 次修复尝试失败时，停止继续打补丁，回到问题建模：重新检查需求预期、数据状态、调用链、依赖服务、缓存 / 异步 / 并发、最近改动和测试环境。仍无法收敛时，转人工或返回上游流程，不继续猜修。

## 前置条件处理

优先复用已有上下文和流程产物，不重复执行已完成阶段。

如果已有失败测试、错误日志、代码范围、测试报告或 `progress.json` 阻塞问题，直接基于这些信息定位和修复。

如果没有前置条件，只补齐修复所需的必要上下文；可以按需参考 `context-scan`、`code-implement`、`code-review`、`test-design-lite` 或 `test-run-lite` 的做法，但不要为了形成流程闭环而读取或执行无关阶段。

如果来自 `auto-dev` 流程中测试失败后的回退，先评估失败原因和影响面，再决定修复与复测范围；不要盲目重走全流程。

需要先明确复测场景时读取 `test-design-lite`，只设计缺陷相关关键场景。

实现约束：

- 只改与 bug 修复直接相关的内容。
- 优先复用项目已有实现模式。
- 不用临时补丁掩盖设计问题。
- 没有详细证据，不声称修复已验证通过。

## 最小复测

复测范围由影响面决定，不默认全量回归。

最小复测至少覆盖：

- 原 bug 复现场景，证明问题已修复。
- 受改动直接影响的正常场景。
- 代码改动触及的关键边界或异常场景。

如果改到公共逻辑、数据写入、权限、缓存、MQ、任务、配置、查询或前端页面，按实际影响补充对应调用方、数据、副作用或页面验证。影响面无法判断时，先补充影响面扫描，再确定复测集合。

缺陷修复的复测证据应尽量包含 RED / GREEN：修复前的失败证据，以及修复后的通过证据。只有 GREEN、没有 RED 时，要说明为什么无法取得修复前证据。

## 输出

输出给用户：

- 问题现象。
- RED 证据或无法取得 RED 的原因。
- 根因证据：来自代码路径、日志、测试、数据或配置的具体依据。
- 修复推断：哪些结论是基于证据推导但未被直接证明，以及剩余不确定性。
- 改动范围。
- 修复要点。
- 影响面。
- 最小复测范围及证据。
- 未验证项或剩余风险。
- 是否适合生成提测申请邮件。

## 完成后建议

独立触发本技能时，只提示下一步；被 auto-dev 流程调用时，返回主流程继续调度。

- 已修复但未验证：建议进入 `test-run-lite` 做最小复测。
- 已验证且需要提测：建议进入 `test-request-mail`。
- 影响面较大或共享逻辑风险较高：建议补 `code-review` 或补充对应复测。
