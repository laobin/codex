# plan-write 技能执行检查清单

## 何时使用本清单

每当用户要求撰写开发方案（说"写方案"、"帮我写方案"等）时，按以下清单执行。

---

## 第一步：明确需求信息 ✓

- [ ] 确认功能名称（英文 kebab-case，如 `order-refund`）
- [ ] 确认需求描述（要解决什么、做什么、不做什么）
- [ ] 确认涉及的相关模块和源码路径（可选但推荐）

---

## 第二步：读取上下文 ✓

- [ ] 读取方案规范：`~/.claude/specs/plan.md`
- [ ] 明确评审维度（写作时主动覆盖）：需求理解与边界 / 技术可行性 / 影响面评估 / 数据与状态一致性
- [ ] 读取相关全局文档：`AI_DOC/global/`（如存在）
- [ ] 读取相关源码文件（了解现有实现）

---

## 第三步：撰写开发方案 ⭐

### 必选章节检查

- [ ] **1. 业务理解**
  - [ ] 清晰重述需求
  - [ ] 说明"要解决什么问题"
  - [ ] 说明"本次做什么"
  - [ ] 说明"本次不做什么"
  - [ ] 说明"异常场景处理"

- [ ] **2. 功能实现思路**
  - [ ] 按子功能分节
  - [ ] 每节说明"做什么"
  - [ ] 每节说明"为什么这么设计"
  - [ ] 涉及 DDL/接口/SQL 直接写出

- [ ] **3. 改动清单**
  - [ ] 列出所有涉及改动的文件
  - [ ] 列出所有涉及改动的表
  - [ ] 列出所有涉及改动的配置
  - [ ] 用表格清晰展示

- [ ] **4. 验证方式**
  - [ ] 覆盖正常流程验证
  - [ ] 覆盖边界条件验证
  - [ ] 覆盖异常场景验证

### 可选章节（按复杂度添加）

- [ ] 影响面分析（大改动时必需）
- [ ] 扩展性考虑（长期维护时必需）
- [ ] 回滚方案（高风险时必需）
- [ ] 附录（补充信息）

---

## 第四步：自检 ✓

### 需求维度

- [ ] 需求理解准确、无歧义
- [ ] 功能边界清晰（做什么/不做什么）
- [ ] 异常场景已考虑（处理策略已说明）

### 技术维度

- [ ] 实现路径清晰、可落地
- [ ] 基于现有技术栈（无技术跳跃）
- [ ] 关键实现细节已说明

### 影响面维度

- [ ] 涉及的接口已说清
- [ ] 涉及的数据表已说清
- [ ] 涉及的缓存/配置已说清
- [ ] 上下游依赖已评估

### 数据一致性维度

- [ ] 状态流转逻辑清晰
- [ ] 并发问题已考虑
- [ ] 历史数据兼容性已考虑
- [ ] 数据回滚策略已说明（如需要）

---

## 第五步：创建目录并写入文件 ✓

- [ ] 创建目录：`AI_DOC/features/<功能名>/`
- [ ] 创建文件头部：
  ```
  > 日期：YYYY-MM-DD
  > 模型：当前模型
  ```
- [ ] 写入方案内容到：`AI_DOC/features/<功能名>/1-plan.md`

---

## 第六步：向用户汇报 ✓

- [ ] 输出方案文件路径
- [ ] 输出章节结构摘要
- [ ] 说明用户可以运行 `/plan-review` 进行下一步
- [ ] 提醒用户确认方向正确后再评审

---

## 关键检查点

### ❌ 禁止事项

- [ ] ❌ 不要模糊需求边界
- [ ] ❌ 不要遗漏关键的异常场景
- [ ] ❌ 不要提出超出技术栈的解决方案
- [ ] ❌ 不要模糊说"会处理并发"，要说具体方案
- [ ] ❌ 不要遗漏影响的模块和表

### ✅ 必须事项

- [ ] ✅ 清晰的业务理解
- [ ] ✅ 明确的功能边界
- [ ] ✅ 具体的实现思路（不是概念，是代码级）
- [ ] ✅ 完整的改动清单（文件、表、配置）
- [ ] ✅ 可验证的验证方式（正常、边界、异常）

---

## 常见问题排查

| 问题 | 处理方式 |
|------|---------|
| 需求不清楚 | 停下来，和用户确认清楚再写 |
| 不知道怎么实现 | 读源码，理解现有实现，参考或改进 |
| 涉及太多模块 | 这很正常，但要清晰说明每个模块的改动 |
| 不知道怎么验证 | 写出你能想到的所有验证点，评审时会补充 |
| 写得太细了 | 不是问题，细节多比遗漏好，评审时可精简 |

---

## 质量标准

### 方案完成度

| 项目 | 标准 |
|------|------|
| 需求理解 | 能复述需求，无遗漏 |
| 技术方案 | 每个改动点都有实现细节 |
| 影响评估 | 涉及的模块都说清楚 |
| 验证方式 | 每个场景都有验证步骤 |

### 内容质量

| 项目 | 标准 |
|------|------|
| 清晰度 | 读者第一遍能理解 |
| 完整度 | 没有"请自行实现"的地方 |
| 可验证性 | 验证方式能实际执行 |
| 可落地性 | 方案基于现有技术栈 |
