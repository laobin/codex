# 功能开发方案撰写

## 目标

产出一份可执行的方案合同，约束后续实现与验证。优先复用当前 scope 已有的需求与上下文文档；缺失时自行完成等价理解，不强制补文档。

## 工作 scope

本技能在"当前 scope 目录"下读写，由调用方指定：

| 模式 | 当前 scope | 输入 | 输出 |
|---|---|---|---|
| feature 根 | `AI_DOC/features/<功能名>/` | 用户描述 + `0-context.md`（若存在） | `<scope>/1-plan.md` |
| PRD 产物 | `AI_DOC/features/<功能名>/deliverables/<n>-产物/` | 当前 scope 的 `README.md`（产物需求/边界/契约）+ feature 根的 `blueprint.md`（全局约束） | `<scope>/1-plan.md` |

PRD 产物模式下额外硬约束：

- `blueprint.md` 的全局约束（命名 / 状态 / 错误码 / 安全 / 监控 / 兼容）必须遵守，禁止重新发明。
- 产物 README 中"暴露契约"与"消费契约"是硬边界，方案不得越界声明其他产物的实现。

## 门禁

继续：

- 已具备足够任务理解（来自 scope 内的上下文或等价确认）。
- 不需要用户澄清。
- 当前假设不影响实现路径。

暂停：

- 任务理解明显不足，无法判断方案边界。
- 存在会改变接口设计、数据写入、状态流转、副作用处理或验证方式的不确定点。
- PRD 模式下与 blueprint 全局约束或产物契约边界冲突。

暂停时输出阻塞原因和缺失信息，由调用方决定回到哪一步。

## 工作重点

可参考 `~/.claude/specs/plan.md` 规范、`AI_DOC/global/` 文档、相关源码；没有则自行完成必要理解，不强制补文档。

方案不是重新做需求扫描，也不是写大而全说明文。只写会影响实现、评审和验证的关键决策。

严格按照 `specs/plan.md` 规范撰写，写完后对照评审维度自检：

- 需求理解与边界是否清晰？
- 技术路径是否可落地？
- 影响面是否说清楚？
- 数据一致性是否考虑到？

**必选章节**：

1. **业务理解**：用自己的话重述需求，包含"要解决什么问题"、"本次做什么"、"本次不做什么"、"异常场景处理"
2. **功能实现思路**：按子功能分节，每节写"做什么"和"为什么这么设计"，涉及 DDL/接口/SQL 直接写出
3. **改动清单**：所有涉及改动的文件、表、配置列成表格
4. **验证方式**：覆盖正常流程 + 边界/异常场景

可按复杂度增加"方案依据 / 关键假设 / 数据状态与副作用 / 风险处理 / 回滚方案"等章节；简单功能不要为了凑章节写空话。

PRD 产物模式下额外要求：

- 方案开头列出本产物消费的 blueprint 全局约束清单（哪些项已遵守、如何遵守）。
- 改动清单中标注哪些是产物 README 声明的"暴露契约"对应实现。

## 输出

写入：`<scope>/1-plan.md`

文件头部固定格式：

```markdown
> 日期：YYYY-MM-DD
```

输出必须让下游明确：

- 本次实现范围是什么，不实现什么。
- 入口、主流程、关键数据流是什么。
- 复用哪些现有模式，避开哪些已有问题。
- 哪些是假设，哪些是已确认事实。
- 如何验证方案真的落地。

## 完成后建议

独立触发本技能时，只提示下一步；被编排流程调用时，返回主流程继续调度。通常建议进入方案评审；如果仍有影响实现路径的未决问题，建议先补足上下文或请用户澄清。
