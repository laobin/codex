# 功能开发方案撰写

## 目标

产出一份服务于 `code-implement` 和 `plan-review` 的可执行方案合同。优先复用 `0-context.md` 已确认的任务理解；没有时自行完成等价理解，不强制补文档。

## 门禁

继续：

- 已具备足够任务理解（来自 `0-context.md` 或等价确认）。
- 不需要用户澄清。
- 当前假设不影响实现路径。

暂停：

- 任务理解明显不足，无法判断方案边界。
- 存在会改变接口设计、数据写入、状态流转、副作用处理或验证方式的不确定点。

返回上游：

- 任务理解本身不清楚，返回 `context-scan`。
- 方案写作中发现关键业务规则缺失，返回 `context-scan` 或请求用户澄清。

## 工作重点

可以参考对应功能目录下的 `0-context.md`、`~/.claude/specs/plan.md` 和必要的 `AI_DOC/global/` 文档或源码；没有则自行完成必要理解，不强制补文档。

方案不是重新做需求扫描，也不是写大而全说明文。只写会影响实现、评审和验证的关键决策。

严格按照 `specs/plan.md` 规范撰写，写完后对照评审维度自检：

- 需求理解与边界是否清晰？
- 技术路径是否可落地？
- 影响面是否说清楚？
- 数据一致性是否考虑到？

**必选章节**：

1. **业务理解**：用自己的话重述需求，包含"要解决什么问题"、"本次做什么"、"本次不做什么"、"异常场景处理"
2. **功能实现思路**：按子功能分节，每节写"做什么"和"为什么这么设计"，涉及 DDL/接口/SQL 直接写出
3. **改动清单**：所有涉及改动的文件、表、配置列成表格
4. **验证方式**：覆盖正常流程 + 边界/异常场景

可按复杂度增加“方案依据 / 关键假设 / 数据状态与副作用 / 风险处理 / 回滚方案”等章节；简单功能不要为了凑章节写空话。

## 输出

写入：`AI_DOC/features/<功能名>/1-plan.md`

文件头部固定格式：

```markdown
> 日期：YYYY-MM-DD
```

输出必须让下游明确：

- 本次实现范围是什么，不实现什么。
- 入口、主流程、关键数据流是什么。
- 复用哪些现有模式，避开哪些已有问题。
- 哪些是假设，哪些是已确认事实。
- 如何验证方案真的落地。

## 完成后建议

独立触发本技能时，只提示下一步；被 auto-dev 流程调用时，返回主流程继续调度。通常建议进入 `plan-review`；如果仍有影响实现路径的未决问题，建议先回到 `context-scan` 或请用户澄清。
