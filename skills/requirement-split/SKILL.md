# 需求任务拆分

## 目标

把用户给出的需求整理成一份可执行的任务拆分文档。重点是明确每个任务的需求、目标、边界、依赖和验收标准，让后续方案、开发、测试或多 agent 并发执行时不漏规则、不抢文件、不丢集成风险。

本技能只做拆分和预检，不写详细实现方案，不修改代码，不执行测试。

## 输入理解

先从用户输入中提取以下信息：

- 需求背景：为什么要做，涉及哪些参与方或业务对象。
- 需求目标：最终要达成什么业务结果。
- 已知约束：权限、状态、数据、兼容、性能、外部依赖、禁止事项。
- 验收标准：用户、接口、数据、状态、日志、任务、测试等角度如何证明完成。
- 未决问题：缺少后会影响拆分、边界或验收判断的信息。

如果用户没有显式写“验收标准”，从需求中推导可观察结果；不能推导时列入待澄清问题，不编造业务规则。

## 拆分原则

- 先拆业务主链路，再拆开发任务。
- 每个任务必须有单一清晰目标，能独立理解、独立验收。
- 按职责边界拆分，优先避免多个任务同时负责同一配置、同一入口、同一状态机或同一共享资源。
- 涉及数据写入时，验收标准必须写清新增、更新、保持不变和失败时副作用。
- 涉及状态流转时，必须写清触发入口、前置状态、目标状态、非法状态处理。
- 涉及鉴权、签名、权限、幂等、并发、定时任务、外部回调时，必须作为全局约束或集成风险列出。
- 多 agent 并发开发时，必须写明共享文件、共享配置、公共模型、路由、迁移、测试脚本等 owner 或合并要求。

## 输出格式

优先输出 Markdown 文档。用户指定路径时写入指定路径；未指定时只在回复中输出。

建议结构：

```md
# 需求任务拆分

## 业务主链路
- <按用户视角描述主流程>

## 全局约束
- <所有任务都必须遵守的规则>

## 任务列表

### 任务 A：<名称>
#### 需求
<这个任务要解决什么>

#### 目标
<完成后应达到什么结果>

#### 边界
<负责什么，不负责什么；共享资源 owner 如有需要也写清>

#### 依赖
<依赖哪些任务、数据、接口、配置或外部条件>

#### 验收标准
- <可观察、可测试、可判断的结果>
- <失败场景和副作用要求>

## 集成验收清单
- <跨任务完整链路验收>

## 冲突风险预检
- <共享文件/共享资源/状态机/ID 生成/接口字段/测试覆盖风险>

## 待澄清问题
- <没有答案会影响拆分或验收的问题>
```

## 验收标准写法

验收标准要尽量落到结果，不写空泛描述。

优先使用：

- 调用什么入口后，返回或展示什么结果。
- 哪些数据被创建、更新或保持不变。
- 状态从什么变成什么。
- 重复提交、并发、失败、超时、无权限时的结果。
- 哪些信息不能对外返回。
- 哪些日志、事件、消息或任务记录必须存在。

避免只写：

- “完成接口开发”
- “保证稳定”
- “处理异常”
- “优化体验”

## 冲突预检清单

输出前检查这些问题：

- 是否有两个任务同时主责同一共享文件或共享配置。
- 是否有 ID、编号、路径、对象 key、状态枚举等生成规则无人负责。
- 是否有接口字段写入了数据库但后续读取方没有使用，或读取方需要字段但无人写入。
- 是否有状态值定义了但无人流转、无人消费、无人测试。
- 是否有失败路径会产生部分写入、重复写入或不可回滚副作用。
- 是否有权限、验签、鉴权、用户隔离或租户隔离遗漏。
- 是否有定时任务、回调、重试、幂等、并发领取等异步边界未验收。
- 是否有测试只覆盖成功主链路，未覆盖失败、重复、并发、超时、非法状态。

## 与其他技能配合

- 需要把拆分后的单个任务写成实现方案时，再使用 `plan-write`。
- 需要批量自动开发时，先用本技能拆分任务，再交给 `auto-dev-batch`。
- 需要评审拆分或方案风险时，再使用 `plan-review` 或 `solution-review`。
