# 关键测试执行

## 目标

执行关键测试场景并记录详细证据，判断当前改动是否满足需求目标或需要回退。

## 工作 scope

本技能在"当前 scope 目录"下读写：

| 模式 | 当前 scope | 参照文档 | 输出 |
|---|---|---|---|
| feature 根 | `AI_DOC/features/<功能名>/` | `4-test-design-lite.md`、`3-code-review.md`、`1-plan.md` | `<scope>/5-test-run-lite.md` |
| PRD 产物 | `AI_DOC/features/<功能名>/deliverables/<n>-产物/` | 当前 scope 的 `4-test-design-lite.md`、`3-code-review.md`、`1-plan.md`、`README.md`；同时可回看 feature 根的 `blueprint.md` 的集成验收 | `<scope>/5-test-run-lite.md` |

fast 通道无测试设计时，使用 `3-code-review.md` 和 scope 推导 1 到 3 个关键场景。

## 门禁

继续：

- 测试场景可执行。
- 测试环境、接口、数据库、日志或副作用验证路径可用。

暂停：

- 测试环境不可访问。
- 接口不可调用。
- 数据库结果无法验证。
- 日志或副作用无法验证，而结论依赖这些证据。

暂停时记录阻塞原因和缺失证据，由调用方决定回到哪一阶段。

## 工作重点

结论必须有详细证据支撑。证据不足只能写"待确认"，不能声称通过。没有详细证据，不得把结论写为通过。

> **编号 / 证据槽位 / 状态词以 `~/.claude/specs/test.md` 为单一权威**。下文为速查，若与 specs/test.md 不一致，以 specs/test.md 为准。各 feature 自定义的 `test-execution-standard.md` 等作业指导书也必须服从该约定（统一 `TC-<scope>-NN` 编号、七槽位、三态状态词）。

### 证据七槽位

关键结论（尤其"通过"）的取证必须包含以下七项，便于第二人复跑核对：

- ① 请求原文：可复跑的 curl/命令（密钥脱敏）+ 返回码 + 关键 id（如 request_id）。
- ② 取证原样：SQL/命令原样 + 真实返回行（带主键 id），不转述、不概括。
- ③ 前后基线：状态/数值变更类给 before/after 两值 + 差值；计费/额度类给 used_quota（或余额）前后值 + 差值，不只贴单值。
- ④ 时间戳同源：请求时刻与落库/日志时间对齐，证明是本次产生。
- ⑤ 一致性实算：等号两边真实取值并排（如 Δused_quota=12 == Σlog.quota=12），不只写"一致"。
- ⑥ 负向对照：关掉条件/改坏输入/越权身份后，结论翻转为失败/被拒，证明这条测试有判别力；翻不转即这条"通过"不成立。
- ⑦ 复跑一致：并发/缓存/额度/幂等类关键场景执行 2 次，结果稳定；不稳定记为缺陷而非通过。

槽位适用性：①② 对所有关键结论必填；③④⑤ 按变更/计费类场景必填；⑥ 对每条关键"通过"断言必填；⑦ 对并发/缓存/幂等类必填。不适用的槽位写明原因。

②取证补充：优先用稳定业务锚点（`request_id`/主键）做跨表串联取证（如 `WHERE request_id IN (...)` 关联多表），保证第二人照锚点原样复跑。

### 逐 TC 执行（消费测试设计）

测试执行必须逐条消费 `4-test-design-lite.md` 中的每个 `TC-<scope>-NN`：不得自创场景，不得漏执行设计中任一关键 TC。设计字段与执行义务、证据槽位严格对应：

| 设计字段 | 执行义务 | 证据槽位 |
|---|---|---|
| TC 编号 | 结果用同一编号回链，一一对应 | 报告标题 |
| 来源 | 原样带入结果 | — |
| 覆盖层 | 确认该层被实际执行，设计有的层不得跳过 | — |
| 前置/造数 | 按设计造数并记录真实 data_id / 状态 | ②③ |
| 操作 | 严格执行设计的操作/请求，不改参数 | ① |
| 正向预期 | 用执行前写定的预期与实际值并排比对，禁止按结果改预期 | ⑤ |
| 负向对照 | 实际执行对照实验，确认结论翻红；翻不转则该 TC 不通过 | ⑥ |
| 证据来源 | 按设计指定的接口/表/日志取证，不替换取证位置 | ② |
| 通过判据 | 用设计的可证伪判据裁定 通过/失败/待确认 | ⑤⑥ |

设计未覆盖、但执行中发现的新风险，单列为"补充场景"，不混入原 TC。

### 单条 TC 执行结果模板

```
### TC-<scope>-NN <场景名>  结论：通过 | 失败 | 待确认
- 回链来源：<同设计的来源>
- 操作①：<可复跑命令(脱敏) + 返回码 + request_id>
- 取证②：<SQL/命令原样 + 真实返回行(带 id)>
- 基线③：<before / after / Δ>（变更/计费类必填）
- 同源④：<请求时刻 ≈ 落库/日志时间>
- 实算⑤：<正向预期 == 实际，等号两边并排取值>
- 负向⑥：<对照操作 + 结论是否翻红>
- 复跑⑦：<2 次结果是否稳定>（并发/缓存/幂等类必填）
- 判据裁定：<引用设计的通过判据，给出 通过/失败/待确认 + 理由>
```

### 测试环境准备

执行测试前先确认被测服务和依赖是否可用。

若项目服务未启动：

- 优先读取项目 `AGENTS.md`、README、`AI_DOC/global` 或 runbook 中的启动方式。
- 按项目规则尝试启动本地服务。
- 启动前检查端口占用和已有进程，避免重复启动。
- 启动后用健康检查、接口探测或日志确认服务可用。
- 无法启动时，记录启动命令、失败日志、阻塞原因，不声称测试通过。

若测试涉及前端页面：

- 优先读取项目 `AGENTS.md`、README、前端目录说明或 runbook 中的前端启动方式。
- 前端服务未启动时，按项目规则尝试启动本地前端服务。
- 使用 Playwright MCP 打开页面、操作表单 / 按钮 / 列表 / 详情 / 弹窗，并记录页面断言。
- 优先使用 `browser_snapshot` 获取页面结构和可交互元素；需要视觉证据时使用 `browser_take_screenshot` 保存截图。
- 需要覆盖不同视口时，使用 `browser_resize` 验证桌面 / 移动端关键页面。
- Playwright 无法访问页面时，记录 URL、启动命令、错误信息和阻塞原因，不声称页面验证通过。

### 测试数据准备

执行依赖数据状态的场景前，必须准备并记录测试数据。

- 不要求清理造出的测试数据；不清理时要保证数据可识别，并记录可能影响。
- 其次使用业务接口造数，保证走真实校验和默认值逻辑。
- 直接写数据库造数只能在本地或环境 IP / 标识包含 `254` 时执行，必须说明表、字段、关联关系、创建命令或 SQL。
- 造数必须可追踪：记录数据 ID、关键字段、初始状态、创建命令或 SQL。

干扰隔离与还原：

- 为隔离被测行为而临时改动的前置（如临时禁用某渠道避免 fallback、临时造对照渠道/账号），必须写明隔离手法与原因。
- 临时改动测后必须还原（贴还原后状态），或明确记录残留及影响；临时数据要么清理（贴 `count=0` 类证据）要么标记可识别。
- 未记录隔离手法的结论存在串扰风险，相关"通过"需降级或复测。

执行时按优先级处理：

- 核心主流程。
- 高风险点。
- 关键异常。

每条场景记录实际命令、输入、结果和证据。只运行命令但没有记录关键输出，不算有效证据。不要假装执行，不编造结果。

环境不可用时，输出阻塞结论，不推断结果。

## 执行自检 gate（全过才允许给出"通过"）

- [ ] 每条"通过"结论的槽位按适用性补齐（①② 必有，⑥ 对关键断言必有）
- [ ] 负向对照已实际执行并翻红，不是口头声明
- [ ] 并发/缓存/幂等类已复跑 2 次且稳定
- [ ] 设计中的每个关键 TC 都有对应执行结果，无遗漏
- [ ] 每条结果用同一 TC 编号回链，操作/取证位置与设计一致，未私改预期
- [ ] 证据不足的场景标"待确认"，未被写成通过

未过项不得给出通过结论。

## 输出

写入：`<scope>/5-test-run-lite.md`

报告必须包含：

- **需求验收矩阵（置顶必产）**：把设计中每条需求/TC 收成一行 `需求/TC │ 结论 │ 证据锚点(request_id/主键/场景号)`，每条至少一行、不漏项；验收人只读这张矩阵即可扫检，要深挖再顺锚点下钻到逐 TC 证据。
- **环境/开关快照（涉及开关/配置会影响结论时置顶产出，否则可省略）**：记录影响结论可复现的开关/配置**真实取值**（非"已开启"）+ 一行脱敏声明（明文凭据/密钥/DB 连接未写入报告）。与结论无关的纯展示类改动无需此表。
- 执行场景数、通过、失败、待确认数量。
- 每条场景的操作步骤、接口结果、数据结果、关键字段、状态/副作用结果。
- 每条关键结论的证据七槽位（按适用性补齐），按「单条 TC 执行结果模板」逐 TC 输出。
- 负向对照与复跑结果。
- 设计中每个关键 TC 的执行结果（同编号回链，无遗漏）；执行中新增风险单列为补充场景。
- 测试数据准备方式、数据 ID、关键字段、初始状态、创建命令或 SQL。
- 涉及前端页面的场景，记录 Playwright 操作、页面断言、截图或 snapshot 证据。
- 证据。
- 问题清单与评级。
- 是否满足需求目标。
