# 代码实现

## 目标

按已确认范围把方案落地成小范围、完整、可验证的代码改动。

## 门禁

继续：

- 实现范围清楚。
- 方案或 scope 足以判断要改什么、不改什么。

暂停：

- 方案缺关键细节，无法安全落地。
- 方案与现有架构或业务规则冲突。
- 实现中发现影响范围明显扩大。
- 出现可能导致数据错乱、状态逆流、重复写入、关键副作用不一致的风险。
- 如果实现中发现正确做法明显超出当前范围，不要用临时补丁绕过去；暂停说明风险、影响和建议路径。

返回上游：

- 任务理解问题：返回 `context-scan`。
- 方案设计问题：返回 `plan-write` / `plan-review`。

## 工作重点

可以参考对应功能目录下的 `0-context.md`、`1-plan.md`、`2-plan-review.md`、`4-test-design-lite.md` 和 `progress.json` 的范围 / 状态 / 阻塞问题；fast 通道没有方案时，以 scope 和当前上下文为实现约束。

动手前先确认：

- 本次只改哪些文件。
- 为什么必须改这些文件。
- 哪些文件不能碰。
- 验证方式是什么。

只实现已确认范围，不擅自扩需求，不重新发明方案，不顺手重构无关代码。除需求相关内容外，不修改任何代码、注释、格式、空白、导入顺序、文件名、配置或标点。

实现时优先复用项目已有模式。必要时补齐：

- 参数校验、边界保护、异常处理。
- 数据写入完整性、事务、幂等、防重、并发保护。
- 状态合法性和历史兼容。
- 缓存、MQ、定时任务、外部系统等副作用一致性。
- 关键路径可排查日志。

不要堆砌无意义保护；只补本次风险需要的关键保护。

## 后端专业要求

实现后端逻辑时，必须保持生产数据量和长期维护视角：

- 优先复用已有接口、Service、Mapper、工具类、转换器、异常处理和校验模式；已有能力能满足时，不新增平行实现。
- 查询逻辑必须考虑数据量增长后的表现；涉及筛选、排序、关联、分页、统计时，检查是否需要索引支持，避免 N+1、循环查库、无界查询和大结果集。
- 写入逻辑必须考虑重复提交、并发、事务边界、部分失败和历史数据兼容。
- 代码应简洁直接，但不能把所有逻辑堆进一个类或一个方法；按现有分层和职责边界组织代码。
- 避免过度抽象、深层嵌套、重复分支，以及为未来假想需求预留结构。
- 减少硬编码，优先沉淀为可复用、可维护的长期能力。
- 不用临时补丁掩盖设计问题；正确做法超出当前范围时，暂停说明风险、影响和建议路径。

## 输出

输出给用户：

- 改动范围摘要。
- 关键实现要点。
- 已知风险 / 限制。
- 建议 `code-review` 重点关注什么。

默认不提交 commit，除非用户或当前流程明确要求；未经用户明确要求，不 push 代码。

## 完成后建议

独立触发本技能时，只提示下一步；被 auto-dev 流程调用时，返回主流程继续调度。通常建议进入 `code-review`；如果实现中发现方案问题，建议回到对应上游阶段。
