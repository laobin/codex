# code-implement 技能执行检查清单

## 何时使用本清单

每当用户触发 code-implement 技能（说"实现方案"、"开发功能"、"写代码"等）时，按以下清单执行。

---

## 第一步：读取方案与评审 ✓

- [ ] 获取项目根目录：`<ROOT> = git rev-parse --show-toplevel 2>/dev/null || pwd`
- [ ] 读取方案文档：`<ROOT>/AI_DOC/features/<功能名>/1-plan.md`
- [ ] 读取方案评审文档：`<ROOT>/AI_DOC/features/<功能名>/2-plan-review.md`
- [ ] 确认本次实现什么
- [ ] 确认本次不实现什么
- [ ] 确认核心主流程是什么
- [ ] 确认评审中要求重点关注什么
- [ ] **关键检查**：是否存在未关闭的 P0 / P1？

### P0/P1 风险评估

- [ ] 如果方案评审中存在未关闭的 P0 / P1 → **停止实现**，输出阻塞原因
- [ ] 如果方案本身无法直接落地 → **停止实现**，列出待确认项

---

## 第二步：识别改动范围 ✓

- [ ] 列出需要改动的文件
- [ ] 列出需要新增的文件
- [ ] 列出涉及的模块
- [ ] 列出涉及的接口 / 页面 / 表 / 状态 / 副作用

### 改动范围评估

- [ ] 改动范围是否尽量小而完整？
- [ ] 是否避免了无关改动？
- [ ] 是否避免了不必要的重构？

---

## 第三步：寻找现有实现模式 ✓

搜索项目现有代码，优先复用：

- [ ] 相似接口实现
- [ ] 相似 service / logic / repository
- [ ] 相似异常处理方式
- [ ] 相似日志结构
- [ ] 相似幂等 / 防重实现
- [ ] 相似状态流转逻辑
- [ ] 相似参数校验方式

### 开发规范检查

- [ ] 阅读 `~/.claude/specs/php-dev.md`（如为 PHP 项目）
- [ ] 阅读 `~/.claude/specs/mysql.md`（如涉及数据库）
- [ ] 代码风格是否符合项目规范？
- [ ] 命名约定是否一致？
- [ ] 文件组织结构是否合理？
- [ ] 接口 / 函数签名是否符合约定？
- [ ] 错误处理是否符合项目模式？

---

## 第四步：实现主流程 ✓

- [ ] 主流程逻辑与方案一致
- [ ] 关键路径可运行
- [ ] 关键输入输出清晰
- [ ] 代码遵循项目开发规范

### 主流程实现清单

- [ ] 方案中要求的所有接口 / 函数都已实现
- [ ] 方案中要求的所有表 / 配置都已修改
- [ ] 主流程的所有步骤都可以执行
- [ ] 关键的业务逻辑已正确实现

---

## 第五步：补强关键保护 ✓

按需补齐以下保护措施：

### 参数与输入处理

- [ ] 必填参数完整性检查
- [ ] 类型校验（不仅依赖框架）
- [ ] 空值处理
- [ ] 非法值处理
- [ ] 边界值处理（长度、大小、范围）

### 数据写入保护

- [ ] 写入目标表明确
- [ ] 关键字段完整性检查
- [ ] 默认值是否合理
- [ ] 重复写入风险评估（幂等、防重）
- [ ] 主表 / 子表 / 聚合数据一致性
- [ ] 必要的乐观锁 / 悲观锁

### 状态流转保护

- [ ] 当前状态合法性校验
- [ ] 目标状态合法性校验
- [ ] 状态机约束遵守
- [ ] 重复提交的防护
- [ ] 状态变化的日志记录

### 副作用一致性

- [ ] 副作用是否按方案触发（缓存 / MQ / 定时任务 / 下游）
- [ ] 失败时是否有处理（重试、降级、告警）
- [ ] 主流程与副作用的一致性保证
- [ ] 必要的可观测性（日志、监控、链路追踪）

### 可观测性

- [ ] 关键请求入口点日志
- [ ] 关键业务逻辑决策点日志
- [ ] 异常捕获与日志记录
- [ ] 必要的上下文字段（user_id、request_id 等）

---

## 第六步：自检与完成 ✓

### 方案一致性

- [ ] 是否严格按方案实现？
- [ ] 是否遗漏方案中的关键要求？
- [ ] 是否忽略方案评审中的重点问题？

### 改动范围

- [ ] 是否只改了必要文件？
- [ ] 是否引入了无关改动？
- [ ] 是否做了不必要重构？

### 开发规范

- [ ] 代码风格是否符合项目规范？
- [ ] 命名约定是否一致？
- [ ] 文件组织结构是否合理？
- [ ] 接口 / 函数签名是否符合约定？
- [ ] 错误处理是否符合项目模式？

### 业务正确性

- [ ] 主流程是否完整？
- [ ] 参数校验是否合理？
- [ ] 数据写入是否完整和正确？
- [ ] 状态流转是否安全？
- [ ] 副作用是否按预期触发？
- [ ] 幂等 / 防重是否实现？

### 工程质量

- [ ] 是否有必要日志？
- [ ] 是否有必要异常处理？
- [ ] 是否保留可排查能力？
- [ ] 是否有明显重复代码 / 脆弱实现？

### 完成输出准备

- [ ] 改动范围摘要已列出
- [ ] 关键实现要点已说明
- [ ] 已知风险 / 限制已标记
- [ ] code-review 重点建议已提出

## 关键检查点

### ❌ 禁止事项

- [ ] ❌ 不要超出方案范围增加功能
- [ ] ❌ 不要改变方案中的业务规则
- [ ] ❌ 不要扩大改动范围
- [ ] ❌ 不要进行无明确理由的大重构
- [ ] ❌ 不要跳过方案评审中已指出的问题
- [ ] ❌ 不要在有 P0 / P1 风险时继续硬写
- [ ] ❌ 不要遗漏关键的参数校验和异常处理

### ✅ 必须事项

- [ ] ✅ 严格按已通过的方案实现
- [ ] ✅ 复用项目现有模式和约定
- [ ] ✅ 补充必要的参数校验
- [ ] ✅ 补充必要的异常处理
- [ ] ✅ 补充必要的日志和可观测性
- [ ] ✅ 补充必要的边界保护
- [ ] ✅ 保持改动尽量小而完整

---

## 问题处理规则

### 发现方案无法直接落地

如果实现过程中发现：
- 方案缺关键细节
- 方案与现有架构明显冲突
- 方案在关键路径上不可实现
- 方案会直接引入明显 P0 / P1 风险

则：
- ❌ 不应继续硬写
- ✅ 停止实现并输出待确认项 / 风险点
- ✅ 回退方案阶段重新评审

### 发现实现中存在明显高风险

如果实现过程中确认会引入：
- 数据错乱
- 状态逆流
- 重复写入
- 关键副作用不一致
- 无法排查的异常黑盒

则：
- ❌ 不应以"先写完再 review"为理由继续推进
- ✅ 在输出中明确标记问题和影响
- ✅ 在实现中补充临时保护措施（如日志、告警）

---

## 常见问题排查

| 问题 | 处理方式 |
|------|---------|
| 需要什么类型的 input validation？ | 参考项目现有实现，遵循 php-dev.md 规范 |
| 怎么处理异常？ | 参考项目现有异常处理，保持一致 |
| 需要加日志吗？ | 关键路径必须有，参考项目日志结构 |
| 遇到并发问题怎么办？ | 方案评审应已考虑，若无则停止 |
| 需要幂等吗？ | 方案评审应已明确，若不明确则停止 |
| 发现 bug 怎么办？ | 小 bug 可修，影响方案的 bug 要停止 |
