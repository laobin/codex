# PRD 整体设计与模块拆分

## 目标

把一份 PRD 史诗级需求切成可独立交付的产物（deliverable），并定义产物之间的契约、依赖与全局约束。

- 产物边界清晰，每个产物可单独验收
- 契约型产物（数据模型、枚举、key 规则、共享约束）优先识别并排在依赖链最前
- 产物之间只交换契约，不渗透实现
- 单产物的实现方案在本产物范围内即可写清，不需要再纵观全局
- 全局约束（命名空间、安全、合规、冲突风险）一次性写清，避免单产物各自发明

blueprint 是 PRD 级"整体视野"产物。它解决的是"拆什么 / 谁先谁后 / 谁负责什么 / 全局规则"，不解决"具体怎么实现"。

## 适用场景

- 需求量级：跨多个模块、领域、外部源或服务。
- 至少能识别出 2 个独立可交付单元。

不适用：

- 单功能、单模块、单接口改动：直接写实现方案，不需要本技能。
- 改动可在单个 worktree 一周内闭环：直接写实现方案，不需要本技能。
- 不涉及多产物契约协调的纯技术债清理：直接写实现方案，不需要本技能。

## 门禁

继续：

- 需求范围、目标、不做什么至少有初步答案。
- 至少能识别出 2 个独立可交付单元。

暂停：

- 需求边界本身有歧义：直接向用户澄清，不要靠假设硬拆。
- 核心业务规则、数据所有权、外部接口可用性未知，导致产物划分会变成猜测。
- 关键名词在用户描述里指代不一致（同一概念多名 / 同一名指多概念），先澄清。

返回用户：

- 需求理解不足、关键信息缺失：向用户提 1-3 个高价值澄清问题，不要继续硬拆。
- 用户描述与已有项目事实冲突：先要求用户确认口径，再决定拆分。

## 工作重点

本技能直接消费用户提交的需求描述，不预设任何前置产出。需要的项目背景信息缺失时，按门禁规则向用户澄清，不要假设。

可选参考（存在则用，缺失不阻塞）：

- `AI_DOC/features/<功能名>/` 下已有上下文文档（若先行做过上下文扫描）
- `AI_DOC/global/` 长期文档、`AI_DOC/modules/` 模块文档
- 相关项目源码入口、已有 feature 目录的历史方案

重点是定边界，不要走入实现细节。

### 1. 先确认值得做 blueprint

不是所有大需求都要 PRD 级拆分。先用一段话回答：

- 这份需求是否真的需要拆成 ≥ 2 个独立产物？
- 是否存在不止一类专业领域（数据模型、采集、计算、展示、调度…）？
- 写成单份实现方案会不会超过一个子代理能消费的范围？

任一答案为否：直接退回到写单份实现方案，不要为流程而流程。

### 2. 切产物的判断标准

每个产物必须满足：

- 一句话能说清做什么 / 不做什么。
- 与其他产物的耦合只在数据契约 / 接口契约 / 共享枚举层面，不在实现细节。
- 单独验收可行：不读其他产物 README 也能判断该产物是否完成。
- 实现工作量介于"半天 ~ 5 天"区间。超出就再拆，低于就合并。

产物数量参考：3 - 10 个。

### 3. 识别契约型产物并前置

契约型产物（如领域数据模型、枚举与 key 规则、全局名称空间、共享 DTO）必须：

- 编号最靠前（通常是 `01-` 或 `01-` / `02-`）。
- 在依赖图中作为多个下游产物的共同前置。
- 不允许"边写下游边改契约"——一旦下游开始消费，契约只能小幅扩展，不允许破坏式修改。

识别契约型产物常见信号：

- 多个产物都需要同一组枚举、id 规则、key 规则、状态枚举。
- 多个产物会读写同一组表或缓存 key。
- 多个产物对外暴露同名 DTO / VO。

漏掉契约型产物的代价：下游产物各自发明枚举与 key，集成时全员返工。

### 4. 产物间依赖与编号

为每个产物指定：

- **产物 ID / 目录名**：`<n>-<产物名 kebab-case>`，编号体现 PRD 主链路顺序。
- **依赖产物**：列出必须先完成的产物 ID。无依赖写"无"。
- **暴露的契约**：本产物对其他产物可见的枚举、表、key、接口、事件、共享 DTO。
- **消费的契约**：本产物依赖其他产物提供的契约。

编号一旦定下，后续产物级方案、任务拆分都会引用，不要随意调。

### 5. 全局约束

在 blueprint 一次性定义所有产物必须遵守的全局规则：

- 命名空间、表前缀、key 前缀。
- 状态枚举与生命周期约定。
- 失败诊断与错误码体系。
- 安全 / 合规 / 数据脱敏要求。
- 监控、日志、可观测性。
- 历史兼容、数据迁移基线。

全局约束一旦定义，每个产物的实现方案都必须消费，不允许产物级重新发明。

### 6. 集成验收

写出 PRD 级集成验收：所有产物都交付后能跑通的最小端到端用例。这是 blueprint 整体成功的硬标准。

### 7. 冲突风险预检

列出最可能在产物间发生的冲突：

- 多产物各自写库、各自定义 key、各自处理失败。
- 契约型产物边界模糊导致下游分歧。
- 同一外部源被多个产物各自调用。
- 数据归属不清，多个产物都认为自己负责某张表。

### 8. 待澄清问题

记录 blueprint 无法靠现有信息回答的问题，分两类：

- **阻塞类**：不回答就无法继续拆分。
- **延后类**：可在单产物实现方案阶段补齐。

阻塞类必须先请用户澄清，不要靠假设硬拆。

## 边界

负责：

- PRD 整体范围理解与边界。
- 产物划分、命名、编号、依赖。
- 契约型产物识别与前置。
- 全局约束（命名 / 安全 / 合规 / 错误 / 观测 / 兼容）。
- 集成验收用例。
- 冲突风险预检与待澄清问题。

不负责：

- 任何具体 SQL、字段、接口签名、状态机内部逻辑——属于产物级实现方案的范畴。
- 任务级拆分与 self-contained 任务卡片——属于任务拆分阶段的范畴。
- 代码实现、评审、测试——属于后续执行阶段的范畴。

## 输出

写入路径：

```text
AI_DOC/features/<功能名>/
├─ blueprint.md                              # PRD 整体设计
└─ deliverables/
    ├─ 00-overview/
    │   └─ README.md                         # PRD 主链路、产物清单、依赖图、全局约束摘要
    └─ <n>-<产物名>/
        └─ README.md                         # 产物总览（需求/目标/边界/依赖/暴露契约/验收）
```

`blueprint.md` 与 `deliverables/00-overview/README.md` 内容互补：前者偏战略叙事与决策依据，后者偏目录索引与契约清单。两份都要写。

所有 README 文件头部固定：

```markdown
> 日期：YYYY-MM-DD
```

## 输出给用户

完成后说明：

- 总产物数、契约型产物数量、可并行产物数量。
- 主链路串行段：哪些产物必须先做。
- 全局约束是否一次性写清，是否有遗漏类目。
- 阻塞类待澄清问题清单。

## 完成后建议

blueprint 通常只写一次。完成后建议先对 blueprint 本身做一轮评审（产物切分合理性、契约完整性、依赖链是否闭合），再按依赖顺序对每个产物分别推进实现方案与开发。

后续阶段若发现 blueprint 划分错误或契约缺失，必须回到本技能修订，不要在单产物层私自补丁。
