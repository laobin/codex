# 关键点测试设计

## 目标

基于方案、评审和风险点，产出一份最小但可验收的关键测试设计。

## 工作 scope

本技能在"当前 scope 目录"下读写：

| 模式 | 当前 scope | 参照文档 | 输出 |
|---|---|---|---|
| feature 根 | `AI_DOC/features/<功能名>/` | `0-context.md`、`1-plan.md`、`2-plan-review.md`、`3-code-review.md` | `<scope>/4-test-design-lite.md` |
| PRD 产物 | `AI_DOC/features/<功能名>/deliverables/<n>-产物/` | 当前 scope 的 `README.md`、`1-plan.md`、`2-plan-review.md`、`3-code-review.md`；同时可回看 feature 根的 `blueprint.md` 集成验收作为产物级测试依据 | `<scope>/4-test-design-lite.md` |

## 门禁

继续：

- 核心主流程和关键风险已明确。
- 能设计出可执行、可观察结果的测试场景。

暂停：

- 方案仍有会影响测试预期的关键歧义。
- 测试无法定义明确输入、操作、数据或结果。
- 关键风险没有可验证路径。

暂停时记录阻塞原因和缺失信息，由调用方决定回到哪一阶段。

## 工作重点

standard / full 需要明确测试预期时优先在实现前执行，standard 保持轻量，full 要求更完整。

测试设计不是测试清单，而是最小验收合同。只设计关键点测试，不追求全量覆盖。

测试设计用于约束实现和测试执行，不是补充测试清单。

优先级：

- 核心主流程。
- P0/P1 风险点。
- 关键异常和边界。
- 必要的前端或接口交互。

不允许只写"返回 200"或"页面正常"。每个场景必须说明为什么必测，以及预期从哪里验证。

每个场景必须能回答：验证什么风险、用什么操作、看什么证据。没有明确证据来源的场景，不进入关键场景。

每个测试场景必须绑定一个来源：需求验收点、方案关键路径、上一阶段评审的 P0/P1 风险、关键异常。

不要根据当前实现反推测试预期；测试预期必须来自需求、方案和风险。

每个场景必须说明：操作输入、观察位置、通过标准和证据类型。无法定义操作、观察位置或通过标准的场景，不进入关键场景；必要时标记为阻塞或待澄清。

场景数量不是目标；优先覆盖能证明核心行为和关键风险被处理的最小集合。

根据风险选择验证层级：纯逻辑用单元测试，接口行为用接口测试，数据一致性看数据库结果，副作用看缓存、消息、任务、日志或下游状态。

涉及前端页面时，必须说明是否需要页面级验证。页面级验证应覆盖关键入口、表单输入、按钮操作、列表 / 详情展示、错误提示、权限可见性和关键状态变化；能用 Playwright MCP 验证的场景，输出可被 Playwright 执行的页面路径、操作步骤、观察点和截图要求。

每个场景必须能被测试执行阶段直接执行或转成执行步骤。

### 测试数据设计

每个依赖数据状态的场景，必须说明测试数据前置条件：

- 不要求清理造出的测试数据，但必须保证数据可识别、可追踪。
- 其次使用业务接口造数，保证走真实校验和默认值逻辑。
- 直接写数据库造数只能在本地或环境 IP / 标识包含 `254` 时执行，必须说明表、字段、关联关系。
- 造数必须可追踪：记录数据 ID、关键字段、初始状态、创建命令或 SQL。

## TDD 强化：可证伪、负向对照、分层、追溯

> **编号 / 证据槽位 / 状态词以 `~/.claude/specs/test.md` 为单一权威**。下文与「关键场景模板」为速查，若不一致以 specs/test.md 为准。场景编号统一 `TC-<scope>-NN`，并与测试执行、总结阶段同号透传。

测试设计的判别力来自"能不能抓到错"，不是"能不能跑通"。每条关键场景按以下要求设计。

### 期望先于实现（红-绿）

- 预期值（返回码、关键字段、数据变更量、状态）必须在执行前写定，并标注预期来源（需求/方案/风险）。
- 禁止根据当前实现或先跑一次的结果反推预期。

### 负向对照（可证伪）

- 每条关键场景必须配一个负向对照：改坏输入、关闭开关、越权身份或构造失败条件后，预期结论应翻转为失败/被拒。
- 负向对照证明这条测试真有判别力；无法设计负向对照的"通过"断言属于弱断言，需说明原因或降级。
- 安全 / 权限 / 越权类场景，负向断言（应被拒、应 401/403、应只见本人数据）就是主断言。

### 分层覆盖自检

- 每个 scope 至少覆盖以下适用层：正常主流程 / 边界 / 关键异常 / 安全·越权 / 并发·幂等。
- 不适用的层要写明为什么不适用，不能默认省略。

### 验证类任务：缺口对照（业务预期 vs 现状）

> 仅当任务是"现有能力验证 / 存量能力核对"（非本次开发新功能）时强制；开发流的增量验收不适用。

验证类任务的目的不是自证"代码就是这么写的"，而是回答"这是不是业务要的"。因此每个**核心需求**除正常主流程 + 负向对照外，必须再设计一条「业务预期 vs 现状」对照判断：

- 先写出**业务期望行为**（来源：需求 / 任务行 / 业务规则），不得用当前实现反推期望。
- 再对照实现实际行为，结论归类为：**满足 / 仅需配置 / 缺口（需开发）**。
- 判为「缺口」必须说明现有能力为何覆盖不了，供总结阶段汇总。
- **不允许只验 happy + reject 即收**：缺少缺口对照的核心需求视为设计未完成。

### 场景编号与追溯

- 每条场景编号 `TC-<scope>-NN`，并绑定来源标识（需求验收点 / 方案路径 / 评审 P0/P1 风险 / 需求项编号如 V-xx 或任务行号）。
- 编号在测试执行和总结阶段透传，用于覆盖率统计与回写。

### 设计自检 gate（全过才允许进入执行）

- [ ] 每条场景预期在执行前写定，非结果反推
- [ ] 每条关键"通过"断言配了负向对照
- [ ] 每条断言可证伪：能说出"实现错了它会怎样红"
- [ ] 分层覆盖已标注适用性
- [ ] 每条场景有 TC 编号与来源绑定
- [ ] 验证类任务：每个核心需求有「业务预期 vs 现状」对照结论（满足 / 需配置 / 缺口）

未过项先修正，不得带病进入执行。

## 关键场景模板（schema）

每条关键场景按以下字段产出，字段缺失即视为设计未完成：

```
### TC-<scope>-NN <场景名>
- 来源：<V-xx / 方案§ / 评审P-x / 任务行号>
- 覆盖层：normal | boundary | error | authz | concurrency
- 前置/造数：<data_id、初始状态、命令或 SQL；无依赖写"无">
- 操作：<可执行步骤 / 请求>
- 正向预期（执行前写定）：<返回码 + 关键字段=值 + 数据变更量>
- 负向对照：<把 X 改坏 / 关开关 / 越权身份 → 预期翻转为 失败 / 被拒>
- 证据来源：<接口 / 表.字段 / 日志 / 副作用>
- 通过判据（可证伪）：<等式或断言，能说明实现错了会怎样红>
```

字段约束：

- `正向预期` 必须在执行前写定，不得留空或写"正常返回"。
- `负向对照` 对每条关键"通过"断言必填；安全 / 越权类场景，负向断言即主断言。
- `通过判据` 必须可证伪，不允许"返回 200""页面正常"这类不可判别的表述。
- `TC 编号` 在测试执行与总结阶段透传，用于覆盖率统计与回写。
- 验证类任务额外补一行 `缺口对照：<业务期望行为 → 现状结论：满足/需配置/缺口（缺口需说明为何覆盖不了）>`。

## 输出

写入：`<scope>/4-test-design-lite.md`

报告必须包含：

- 本次设计针对什么。
- 需求理解和关键风险。
- 3 到 8 条关键测试场景。
- 每条场景的输入、操作、接口预期、数据预期、状态/副作用预期。
- 每条场景的 TC 编号、来源绑定与覆盖层标注。
- 每条关键场景的负向对照设计（让断言翻红的对照实验）。
- 验证类任务：每个核心需求的「业务预期 vs 现状」对照结论（满足 / 需配置 / 缺口），缺口注明为何覆盖不了。
- 每条依赖数据的场景的数据前置条件和造数方式。
- 涉及前端页面的场景，包含页面路径、关键操作、页面断言和截图要求。
- 最小通过标准。
- 是否允许进入测试执行。
