# 关键点测试设计

## 目标

基于方案、评审和风险点，产出一份最小但可验收的关键测试设计。

## 门禁

继续：

- 核心主流程和关键风险已明确。
- 能设计出可执行、可观察结果的测试场景。

暂停：

- 方案仍有会影响测试预期的关键歧义。
- 测试无法定义明确输入、操作、数据或结果。
- 关键风险没有可验证路径。

返回上游：

- 需求或业务规则不清：返回 `context-scan`。
- 方案缺失验收依据：返回 `plan-write` / `plan-review`。
- 实现风险影响测试预期：返回 `code-implement` / `code-review`。

## 工作重点

可以参考对应功能目录下的 `0-context.md`、`1-plan.md`、`2-plan-review.md` 和已存在的 `3-code-review.md`；standard / full 需要明确测试预期时优先在实现前执行，standard 保持轻量，full 要求更完整。

测试设计不是测试清单，而是最小验收合同。只设计关键点测试，不追求全量覆盖。

测试设计用于约束实现和测试执行，不是补充测试清单。

优先级：

- 核心主流程。
- P0/P1 风险点。
- 关键异常和边界。
- 必要的前端或接口交互。

不允许只写“返回 200”或“页面正常”。每个场景必须说明为什么必测，以及预期从哪里验证。

每个场景必须能回答：验证什么风险、用什么操作、看什么证据。没有明确证据来源的场景，不进入关键场景。

每个测试场景必须绑定一个来源：需求验收点、方案关键路径、plan-review/code-review 的 P0/P1 风险、关键异常。

不要根据当前实现反推测试预期；测试预期必须来自需求、方案和风险。

每个场景必须说明：操作输入、观察位置、通过标准和证据类型。无法定义操作、观察位置或通过标准的场景，不进入关键场景；必要时标记为阻塞或待澄清。

场景数量不是目标；优先覆盖能证明核心行为和关键风险被处理的最小集合。

根据风险选择验证层级：纯逻辑用单元测试，接口行为用接口测试，数据一致性看数据库结果，副作用看缓存、消息、任务、日志或下游状态。

涉及前端页面时，必须说明是否需要页面级验证。页面级验证应覆盖关键入口、表单输入、按钮操作、列表 / 详情展示、错误提示、权限可见性和关键状态变化；能用 Playwright MCP 验证的场景，输出可被 Playwright 执行的页面路径、操作步骤、观察点和截图要求。

每个场景必须能被 test-run-lite 直接执行或转成执行步骤。

### 测试数据设计

每个依赖数据状态的场景，必须说明测试数据前置条件：

- 不要求清理造出的测试数据，但必须保证数据可识别、可追踪。
- 其次使用业务接口造数，保证走真实校验和默认值逻辑。
- 直接写数据库造数只能在本地或环境 IP / 标识包含 `254` 时执行，必须说明表、字段、关联关系。
- 造数必须可追踪：记录数据 ID、关键字段、初始状态、创建命令或 SQL。

## 输出

写入：`AI_DOC/features/<功能名>/4-test-design-lite.md`

报告必须包含：

- 本次设计针对什么。
- 需求理解和关键风险。
- 3 到 8 条关键测试场景。
- 每条场景的输入、操作、接口预期、数据预期、状态/副作用预期。
- 每条依赖数据的场景的数据前置条件和造数方式。
- 涉及前端页面的场景，包含页面路径、关键操作、页面断言和截图要求。
- 最小通过标准。
- 是否允许进入测试执行。

## 完成后建议

独立触发本技能时，只提示下一步；被 auto-dev 流程调用时，返回主流程继续调度。允许时建议进入 `test-run-lite`；不允许时建议返回对应上游阶段。
