## 2. 表彰等级标准（固化）

各档**挂钩奖励金额区间**（来自表内图例行）：

| 级别 | 奖励区间 | 定位关键词 |
|------|----------|-----------|
| **A** | 800–5000 元，**黄金勋章** | **核心系统 / 基础设施级，落地范围跨系统/全组，且有量化收益** |
| **B** | 400–2000 元 | **已实际落地**的较有价值的模块 / 重构 / 完整工具 / 体系产出 |
| **C** | 200–500 元 | 常规自发**优化 / 单点改进 / 文档 / 部署步骤 / 流程梳理** |
| **D** | 20–200 元 | 琐碎小优化、零散小事 |

### 评级细则（红线，按优先级从上到下）

0. **落地范围 ＝ 首要权重**（先看这条，再看其他）：评级首先看贡献**被实际采用 / 推广的范围**——被多少人、多少系统真正用起来，是否跨组/全组推广，是否形成强制规范或长期复用。落地范围大的上抬，**仅自用 / 未推广 / 停留在"做了、写了"的下压**。落地范围与技术含量冲突时，**以落地范围为准**。
1. **A 档要素**（需同时满足）：作用于对外核心系统或团队基础设施 ＋ 落地范围跨系统/全组 ＋ **有量化收益**（如响应耗时-30%、CPU/Load-60%、承载能力提升）。缺量化、或只小范围落地 → 顶多 B。
2. **分享会默认 B；纯文档原则上 C**：
   - **分享会**（技术分享、业务分享、思路/设计分享）有知识传递价值，**默认 B**。
   - **纯文档**（业务文档、部署步骤、流程梳理、操作手册、模板）默认 **C**，**不轻易给文档 B**——只有**同时**满足「覆盖多个核心模块的体系性沉淀」且「已在组内/跨组实际落地采用」，才例外考虑 B。
3. **工具 / 自动化按"完整可复用度 ＋ 落地范围"定**：完整可复用工具 + 配套能力（skills/指标体系）**且已被多系统/多人采用** → **B**；单点脚本 / 一次性优化 / 仅自用 → **C**。
4. **被动需求降一档**：`需求=被动需求` 或"公司要求后才做"的，自发性弱，同等内容比"自发需求"降一档评。
5. **横比一致性**：同一作者、相近投入的两条，级别不应明显倒挂。

### 标尺案例（用现有数据校准）

- **A**：堡垒机打通内网运维、kettle 数据中心、ELK 搭建、部署组内 wiki、模板项目后端开发、3-9 应对 3-4 倍负载方案、鲲池 API webman 重写（量化收益）。
- **B**：各类技术/业务**分享会**（鲲池设计分享、模板项目与AI编程分享、ads业务分享会、设计模式分享会、异常流量排查分享会、后端分布式技术分享等，分享会默认 B）、Metricbeat/kibana 监控仪表盘、wss 后台代码生成器、后端开发流程规范制定、中间件内网通信、组内文档输出、组内 AI 开发流程 skills、LLM 上游压测工具（2项目复用）、海外与国内对等连接、短信防盗刷优化。
- **C**：nginx 日志切割、聚宝盆 redis 锁优化、CPU 告警定位处理、wordpress/nuxtjs 部署步骤、微信商户解封流程梳理、各类单模块业务文档、单点接口优化。
- **D**：奖励 20–200 元级别的零散小优化。

## 3. 作业流程

**范围：仅补空级别**——只评 `影响级别` 为空、且未归档的记录；已评级的不动。

1. **取候选**：列全表，筛出 `影响级别` 为空 且 `是否归档≠已归档` 的记录（含 `是否归档` 为空者——这类还被视图隐藏，提示用户应补「未归档」）。
   ```powershell
   & $cli base +record-list --base-token $app --table-id $tbl --as user --format json `
     --field-id "事项" --field-id "姓名" --field-id "需求" --field-id "影响面" `
     --field-id "影响级别" --field-id "是否归档" --limit 200 1>$tmp 2>$null
   $d = (Get-Content $tmp -Raw -Encoding UTF8 | ConvertFrom-Json).data
   # .data.data 行=值数组，按 .data.fields 顺序；.data.record_id_list 取 rid
   ```
   - ⚠️ 别只读视图：`是否归档` 为空的未评级记录不在视图里，会漏评。以**全表 + 影响级别为空**为准。
2. **逐条评级**：依据 `影响面`（结合 `需求`、`姓名`），按第 2 节标准 + 标尺，给出**建议级别 + 一句理由**。
   - **先判落地范围**（被多少人/系统采用、是否跨组/全组推广/成规范），再叠加技术含量/量化收益。
   - 若 `影响面` 没写清落地范围 → 提示用户该条**落地信息不足**，建议先补充再定级（尤其想评 A/B 的）。
   - 边界条目标注"可争 X / 偏低偏高"。
3. **出提案表**（不写）：列 `事项 | 姓名 | 当前(空) | 建议级别 | 理由`，交用户确认。
4. **确认后写回** `影响级别`（用户逐条或整体点头后才动）：
   ```powershell
   $body = @{ fields = @{ "影响级别" = "B" } } | ConvertTo-Json -Compress
   & $cli api PUT "/open-apis/bitable/v1/apps/$app/tables/$tbl/records/<rid>" --as user --data $body --json
   ```
   - 单选列的值 = 选项名字符串（"A"/"B"/"C"/"D"）。
   - 多条可循环；或用 `base +record-batch-update`。
5. **复核**：再 `record-list` 拉回已写记录，确认 `影响级别` 落库正确。

## 4. 本表专有坑

| 现象 | 原因 / 解法 |
|------|------------|
| 某条贡献"消失"、视图里找不到 | `是否归档` 为空 → 被视图筛选挡住。数据没丢，全表能查到；补「未归档」即回显 |
| 漏评了一些未评级记录 | 只读了视图。未评级记录常 `是否归档` 也为空 → 不在视图。改为**全表筛 `影响级别` 空** |
| 写 `影响级别` 报 91403 | 用了 bot/tenant；改 `--as user` |
| 想把空奖励/空级别置顶方便评 | 加公式字段 `IF(ISBLANK([奖励]),0,1)` 升序排（数字公式记得用 v1 接口补 `formatter:"0"`，否则字段报错）。详见 feishu-bitable |
