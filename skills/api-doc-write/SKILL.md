# 接口文档生成

## 目标

根据用户提供的接口信息，生成清晰、规范、可直接分享给前端、客户端、后台或第三方系统的 Markdown 接口文档。

输出重点是对接可读性：接口做什么、怎么请求、传什么、返回什么、错误怎么判断、环境域名是什么。

## 信息提取

从用户输入中提取：

- 简要描述：接口用途和使用场景。
- 请求 URL：保留用户给出的变量写法，如 `{{domain}}/api/example`。
- 请求方式：默认沿用用户输入；未给出时标记“待确认”。
- Header：字段名、是否必选、类型、默认值或说明。
- 请求参数：字段名、是否必选、类型、说明。
- 响应参数：字段名、是否必选、类型、说明。
- 成功返回示例：优先使用用户给出的示例；缺失时按字段生成最小示例。
- 失败返回示例：优先覆盖参数异常；必要时补充限流或服务端错误说明。
- 备注：状态码说明、签名说明、域名、调用限制、业务注意事项。

不要编造不确定的业务字段。必须补全但信息不足时，用“待确认”标注。

## 输出格式

严格使用下面的 Markdown 结构。标题层级和表格列尽量保持一致。

```md
##### 简要描述

- <接口用途>

##### 请求URL

- `<请求URL>`

##### 请求方式

- <GET/POST/PUT/DELETE>

##### Header

|header|必选|类型|默认值|
|:-----|:---|:---|:----|
|<header_name>|是/否|<type>|<默认值或说明>|

##### 请求参数

| 参数名 | 必选 | 类型 | 说明 |
|:------|:----|:----|:----|
| <name> | 是/否 | <type> | <说明> |

##### 响应参数

| 参数名 | 必选 | 类型 | 说明 |
|:------|:----|:----|:----|
| <name> | 是/否 | <type> | <说明> |

##### 成功返回示例

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

##### 失败返回示例

```json
{
  "code": 400,
  "msg": "参数错误",
  "data": null
}
```

##### 备注

- code=200 表示后端处理成功
- code=400 表示客户端参数异常
- code=429 表示客户端请求过于频繁
- code=500 表示服务端内部错误
```

## 书写规则

- 字段说明要面向调用方，避免只写数据库或内部实现名。
- 参数必选性不明确时写“待确认”，不要默认写“否”。
- 类型使用调用方能理解的写法，如 `string`、`int`、`bool`、`List<int>`、`List<object>`、`object`。
- Header 没有时保留 Header 小节并写“无”表格行，除非用户要求删除。
- `data` 如果直接返回数组，响应参数可写为业务字段名，也可备注“成功时 data 为 ...”。
- 失败示例至少给一个最常见的参数异常。
- 域名放在备注中，按“测试服域名”“正式服域名”列出。
- 用户提供多个备注标题时，合并为一个“备注”小节。

## 补全策略

当用户只给简短接口需求时，按最小可用文档补齐：

- 请求方式未知：写“待确认”。
- Header 未知：写 `|无|否|string|-|`。
- 签名存在但规则未知：请求参数中保留 `sign`，说明写“签名”。
- 返回结构未知：使用 `{ "code": 200, "msg": "success", "data": null }` 并在响应参数写“待确认”。
- 错误码未知：使用通用 `200/400/500`，不要扩展业务错误码。
