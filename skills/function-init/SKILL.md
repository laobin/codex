# 初始化功能上下文

## 目标

这个技能用于把一个明确的业务功能沉淀成 AI 可读、可检索、可复用的模块级文档。

- 这个功能负责什么、不负责什么
- 需求来了先看哪些入口
- 哪些数据、依赖或页面会影响判断
- 这个功能怎么测
- 有哪些真实历史坑需要避免

输出不是空模板，而是基于仓库证据整理后的功能上下文，帮助后续测试设计、测试执行、缺陷修复和功能迭代少重复探索。

## 工作边界

只写目标模块文档：

```text
AI_DOC/modules/<function-name>/
```

不改业务源码、配置文件、构建脚本、数据库脚本和非目标文档。

功能名无法确定、用户未授权落盘、需要写入密钥 / 真实密码 / 生产数据 / 敏感客户信息，或目标文档已有大量无法合并的手写内容时，先说明原因，不强行覆盖。

## 工作重点

可以参考 `AI_DOC/global/project-context/`、`AI_DOC/modules/<function-name>/`、相关 `AI_DOC/features/` 和 `AI_DOC/batch/` 文档理解功能背景；没有则跳过。

### 1. 确定功能目录

把功能名规范为 kebab-case，写入：

```text
AI_DOC/modules/<function-name>/
  00-module-context.md
  01-module-test-guide.md
  02-known-issues.md
```

如果用户给的是中文名，根据现有代码、路由、feature 文档或页面名推断英文目录。存在多个合理候选时，优先选择已有 feature、batch、route 或 package 中最稳定的名称。

### 2. 先建立证据清单

先扫描证据，再写文档。

优先查：

- 项目级项目地图、业务规则和测试说明。
- 该功能已有 feature / batch / module 文档。
- 后端 Controller、Service、Mapper、VO、配置。
- 前端 API、页面、路由。
- 测试类、SQL、菜单脚本和本地验证记录。

搜索优先使用 `rg` 和 `rg --files`。当证据足够支撑结论时停止，不做全仓库盘点。

### 3. 只写真实功能事实

- 不保留空表。
- 不写“按实际情况填写”“自行启动”“后续补充”这类无效文本。
- 关键事实尽量带文件路径、类名、方法名、接口、命令或文档来源。
- 缺口写成可追踪待确认项：缺什么、查过哪里、为什么不能确认。
- 不把长方案大段复制进模块文档，只做压缩索引和测试入口。

### 4. 填充功能文档

`00-module-context.md` 回答“这个功能什么时候会改、先看哪里”。

文件可以包含：

- 功能定位：负责什么、不负责什么。
- 典型需求信号：3 到 5 个最常见触发场景。
- 关键入口：后端、前端或任务入口，只保留最重要的。
- 关键数据与依赖：会影响判断的主数据、外部依赖、模型、向量库或页面入口。
- 必读相关文档。

不要写完整代码索引、实现教程、业务规则大全或泛泛风险清单。

`01-module-test-guide.md` 回答“这个功能怎么测”。

文件可以包含：

- 项目级测试手册入口。
- 3 到 5 个本功能最关键的验证重点。
- 关键接口或页面入口。
- 测试类地址、覆盖场景和前置条件。
- 前置数据或造数方式。

前置数据优先使用业务接口。允许本地或指定测试环境直接写库造数时，说明表、字段和关联关系；没有稳定造数方式时，不编造，写明需确认。

`02-known-issues.md` 回答“这个功能有哪些历史坑”。

文件可以包含：

- 高优先级问题。
- 回归问题。
- 反复踩坑。
- 废弃做法。
- 经验沉淀。

只写真实发生过、已有文档记录或从代码可证明的问题；不要写泛泛风险清单。

## 输出

最后说明：

- 更新了哪些文件。
- 主要内容来自哪些证据。
- 哪些信息已确认。
- 哪些信息仍待确认，以及已查过哪些证据。
- 是否建议继续进入 `test-design-lite` 或 `test-run-lite`。

不要声称“模块文档完整”。只能基于证据说明本次覆盖范围。

## 完成后建议

只提示下一步，不自动执行。

如果用户目标是测试某个功能，通常建议先进入 `test-design-lite`，再进入 `test-run-lite`。
