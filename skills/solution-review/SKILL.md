# 方案评审

## 步骤

### 1. 确认输入

- 确认方案文档路径存在，且优先为 Markdown 文件
- 确认是否需要结合源码、配置、表结构或现有设计一起评审
- 确定输出路径为方案同级目录下的 `review-{方案文件名}.md`

### 2. 收集上下文

读取并理解以下内容：
- 方案文档本身
- 方案涉及的关键源码文件
- 相关配置、接口、数据库结构、历史设计文档

如果方案中的关键判断依赖源码验证，不要只基于文档表述下结论，必须交叉验证实现或配置。

### 3. 执行评审

以技术方案评审人视角进行严格评审，至少覆盖以下维度，并按需增减：

| 维度 | 关注点 |
|------|--------|
| 根因分析验证 | 根因分析是否正确，是否存在遗漏或错误归因 |
| 方案完整性 | 业务理解、边界定义、前置条件、异常场景是否完整 |
| 技术可行性 | 方案是否能落地，关键设计是否有源码或配置支撑 |
| 影响面评估 | 是否识别到上下游依赖、兼容性、迁移和回归影响 |
| 扩展性 | 方案复杂度是否合适，是否支持后续扩展和复用 |
| 测试覆盖 | 正常流程、异常场景、回归验证、边界场景是否充分 |
| 风险点 | 上线风险、回滚策略、数据一致性、灰度方式是否明确 |

### 4. 输出结果

对每个维度输出：
- 结论：通过 / 有风险 / 不通过
- 说明：具体问题、判断依据或建议
- 建议：改进方向；如果无需改进可省略

最后必须给出：
- 总体评价
- 是否建议通过评审
- 如果不建议通过，明确指出必须补充或修改的项

### 5. 落盘规则

默认将评审结果写入：
`{方案同级目录}/review-{方案文件名}.md`

在落盘完成后，再向用户汇报评审结论和落盘路径。

## 要求

- 优先指出真正影响正确性、可落地性和风险控制的问题
- 结论必须有依据，避免空泛评价
- 如果源码或配置不足以支撑某个判断，要明确说明“当前证据不足”
- 如果没有发现明显问题，也要说明剩余风险和测试空白
- 评审输出写入新的 review 文档，**禁止直接修改原方案文档**
- 评审过程中**禁止修改业务代码、配置文件和测试代码**
