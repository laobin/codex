# 快速开发流程

## 目标

这个技能用于快速完成低风险、小范围、可直接验证的改动。

- 需求目标一眼清楚
- 改动范围很小
- 不需要先写方案才能安全实现
- 不涉及核心数据写入、状态流转、幂等或外部副作用

fast 的重点是最快安全改对，不补方案、不补测试设计、不为了文档闭环执行额外阶段。

## 工作重点

参考路径：

```text
code-implement
code-review
test-run-lite
```

这是推荐路径，不是硬性闭环。已有证据足够时直接推进；缺少证据时补必要上下文；发现不是低风险小改动时立即升级。

- 先用一两句话确认本次改动范围，并写入 `progress.json.scope`。
- 缺陷修复、报错处理或回归问题，按需参考 `bug-fix`。
- 实现时只改需求相关内容，不做不必要的修改。
- 代码评审只关注事故风险、遗漏边界和不可验证点。
- 测试执行只覆盖最关键的 1 到 3 个场景，不默认全量回归。

## 升级判断

出现以下任一情况，不继续按 fast 处理：

- 改动范围无法用一两句话说清。
- 需要扫描业务链路、数据写入、状态规则或外部副作用才能判断。
- 涉及状态流转、幂等、防重、缓存、MQ、定时任务或跨系统。
- 测试或评审暴露方案级问题。
- 同一类实现问题一次修复后仍不收敛。

升级目标：

- 数据写入、影响面扩大、方案不清：升级到 `standard`。
- 状态、一致性、副作用、跨系统：升级到 `full`。

升级前完成 `progress.json` 更新（`current_status="upgraded"`、`upgraded_from="fast"`、`recommended_next_action="auto-dev-standard"|"auto-dev-full"`），并在 `stage_history[].note` 写明目标流程、建议起点、原代码状态（可复用 / 部分复用 / 建议重写）。由主 agent 接力调用目标流程；目标流程先审计已有证据再决定从哪个必要动作接上。

## progress.json

按 `auto-dev` 主入口规范维护状态。

常用阶段：

- `code-implement`
- `code-review`
- `test-run`
- `done`

fast 没有方案阶段，`plan_review_round` 通常保持 0；测试暴露方案问题时直接升级，不在 fast 内反复补方案。

## 输出

最后说明：

- 改了什么。
- 为什么仍属于 fast 范围，或为什么已升级。
- 验证了什么，有哪些证据。
- 未验证项或剩余风险。
- 建议下一步。
