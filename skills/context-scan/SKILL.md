# 上下文扫描

## 目标

把本阶段当成写方案或写代码之前的“任务理解确认 + 代码上下文扫描”。

核心目标是确认任务理解，而不是完成代码盘点。不要穷举阅读整个仓库，要通过记录以下信息，降低后续方案和实现走偏的概率：

- 用户真正要解决的问题是什么
- 本次范围内做什么、不做什么
- 哪些影响会改变方案或实现路径
- 哪些现有代码路径和文档与需求相关
- 哪些项目既有模式应该复用
- 哪些假设、未决问题和风险需要在实现前处理
- 入口初判的流程线是否成立，是否需要升级或阻塞

## 门禁

出现以下情况时，停止并询问用户，不要继续写方案或实现代码：

- 需求目标存在明显歧义，可能导向多个互斥实现
- 必需的外部系统、数据源或业务规则无法从代码 / 文档中推断
- 存在会改变接口设计、数据写入、状态流转、副作用处理或验证方式的不确定点
- 扫描发现会改变流程线的风险，例如状态机、幂等、跨系统副作用或大范围数据迁移，且无法按升级规则安全处理

如果只有轻微未决问题，可以记录明确假设，并允许进入方案阶段。

判断是否需要用户澄清：

- 能从代码 / 文档确认的，不问用户。
- 不确定点不会改变本轮方案或实现路径时，记录明确假设后继续。
- 存在会改变方案或实现路径的不确定点时，必须暂停，提出 1 到 3 个高价值澄清问题，不要继续进入 `plan-write` 或 `code-implement`。

## 工作重点

用户未提供功能名时，从当前分支名推断（去掉 `feature/`、`hotfix/` 前缀）。可以参考已有 `AI_DOC/global/` 和 `AI_DOC/modules/` 文档理解项目背景；没有则跳过。

`0-context.md` 的价值在于让 `plan-write` 和 `code-implement` 不必重复探索同一批上下文。

文件必须包含：

- 简洁的需求重述
- 本次范围内 / 范围外边界
- 影响面、风险点和当前假设
- 相关文件，以及每个文件为什么相关
- 应复用的现有实现模式
- 涉及的数据表、接口、缓存、队列、配置或定时任务
- 可复用代码位置
- 未决问题和风险，以及影响
- 是否需要用户澄清，以及是否允许进入下一阶段的明确结论
- 推荐流程线，以及与入口初判是否一致

- 本阶段只读，不修改源码。
- 控制探索范围。优先读取最相关的 5 到 20 个文件；除非有明确理由，不超过 30 个文件。
- 搜索优先使用 `rg` / `rg --files`。
- 需求涉及已有业务域时，优先参考 `AI_DOC/global/` 下的长期文档。
- 当已有上下文足以写出可信方案时停止，不做全仓库盘点。

## 完成后建议

独立触发本技能时，只提示下一步；被 auto-dev 流程调用时，返回主流程继续调度。允许进入下一阶段时，通常建议进入 `plan-write`；如果是低风险小改动，也可以建议直接进入 `code-implement`。
