# 功能方案评审

## 目标

独立判断 `1-plan.md` 是否足以交给 `code-implement` 安全实现。

## 工作重点

可以参考对应功能目录下的 `0-context.md`、`1-plan.md` 和历史 `2-plan-review.md`；没有 `1-plan.md` 时停止，没有 `0-context.md` 把“缺少任务理解依据”作为风险判断。评审中发现任务理解问题，返回 `context-scan` 或请用户澄清；方案表达或设计问题，返回 `plan-write`。

不要评“文档写得是否漂亮”，而是评“这个方案能不能放心交给实现”。

重点检查：

- 需求理解与边界是否继承 `0-context.md`。
- 技术路径是否可落地。
- 影响面是否完整。
- 数据、状态、副作用和兼容性是否说清楚。
- 验证方式是否可执行。

不要替方案作者补全缺失逻辑。方案没有写清的数据流、状态规则、副作用、验证方式，按缺失处理。

问题级别按 `AGENTS.md` 的 P0/P1/P2/P3 公共标准判断。P0/P1 不是“我觉得有风险”，必须说明失败路径、影响和应回到哪个上游阶段。

## 输出

写入：`AI_DOC/features/<功能名>/2-plan-review.md`

若文件不存在，创建文件头；若已存在，追加新一轮评审并保留历史。

报告必须包含：

- 本轮评审结论：通过 / 有条件通过 / 不通过
- P0/P1/P2/P3 问题清单
- 上轮 P0/P1 修复确认（第 2 次起）
- 是否允许进入 `code-implement`
- 若不允许，返回 `context-scan` 还是 `plan-write`

## 完成后建议

独立触发本技能时，只提示下一步；被 auto-dev 流程调用时，返回主流程继续调度。通过时建议进入下一阶段；不通过时建议修复方案，或先进入 `test-design-lite` 暴露关键风险。
