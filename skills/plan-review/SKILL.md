# 方案评审

## 目标

独立判断方案文档是否足以支撑下一步动作：

- 评审 blueprint 时：判断产物划分是否合理、契约是否完整、依赖链是否闭合，能否进入逐产物开发。
- 评审实现方案（1-plan.md）时：判断是否足以安全进入实现。

## 工作 scope 与评审对象

由调用方指定评审对象；未指定时按下表自动识别：

| 当前 scope | 评审对象 | 输出文件 |
|---|---|---|
| feature 根，存在 `blueprint.md` 且无 `1-plan.md` | `blueprint.md` | `<scope>/blueprint-review.md` |
| feature 根，存在 `1-plan.md` | `1-plan.md` | `<scope>/2-plan-review.md` |
| 产物子目录（`.../deliverables/<n>-产物/`） | 当前 scope 的 `1-plan.md` | 当前 scope 的 `2-plan-review.md` |

无法识别评审对象、或目标文档缺失时停止。

## 工作重点

不要评"文档写得是否漂亮"，而是评"这个方案能不能放心进入下一步"。

### 评审 blueprint

重点检查：

- 产物切分是否合理：每个产物单一职责、可独立验收、工作量适配。
- 契约型产物是否前置、契约是否覆盖所有共享枚举 / key / DTO / 接口 / 事件。
- 依赖链是否闭合、无环、可执行。
- 全局约束是否完整（命名、状态、错误码、安全、监控、兼容）。
- 集成验收用例是否能证明 PRD 整体完成。
- 冲突风险与待澄清问题是否真实可处理。

常见漏洞：产物边界模糊、契约缺失、依赖成环、全局约束缺类目——必须在进入产物级开发前修复。

### 评审实现方案（1-plan.md）

可参考当前 scope 下的上下文文档（`0-context.md` 或产物 `README.md`）、历史评审与 PRD 模式下的 `blueprint.md`。

重点检查：

- 需求理解与边界是否清晰、是否与上下文一致。
- 技术路径是否可落地。
- 影响面是否完整。
- 数据、状态、副作用和兼容性是否说清楚。
- 验证方式是否可执行。
- PRD 产物模式下：是否消费 blueprint 全局约束、是否遵守产物 README 的契约边界。

不要替方案作者补全缺失逻辑。方案没有写清的数据流、状态规则、副作用、验证方式，按缺失处理。

问题级别按 `AGENTS.md` 的 P0/P1/P2/P3 公共标准判断。P0/P1 必须说明失败路径、影响和应回到哪个上游阶段。

## 输出

按上表写入对应文件。若文件不存在创建文件头；已存在则追加新一轮评审并保留历史。

报告必须包含：

- 本轮评审结论：通过 / 有条件通过 / 不通过。
- P0/P1/P2/P3 问题清单。
- 上轮 P0/P1 修复确认（第 2 次起）。
- 是否允许进入下一阶段。
- 不允许时，应回到哪一阶段补齐。

## 完成后建议

独立触发本技能时，只提示下一步；被编排流程调用时，返回主流程继续调度。通过时建议进入下一阶段；不通过时建议修复方案或回到上一阶段。
